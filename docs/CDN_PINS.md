# Third-party scripts: pins and integrity hashes

Barcode reading and the backup digit reader load from jsDelivr on first use. They are pinned to exact versions, and the two script loads carry Subresource Integrity (SRI) hashes. The code is in `index.html` (constants `POLY_JS`, `POLY_SRI`, `POLY_ESM`, `TESS_JS`, `TESS_SRI`, `TESS_LANG`). The check is `tests/cdn-pins.test.cjs`.

| What | Pinned to | Integrity |
|---|---|---|
| Barcode reader (script tag) | `barcode-detector@3.2.3`, `dist/iife/ponyfill.js` | sha384 hash in `POLY_SRI` |
| Barcode reader (ES module fallback) | `barcode-detector@3.2.3`, `dist/es/ponyfill.js` | none: `import()` cannot take a hash |
| ZXing WebAssembly (fetched by the barcode reader) | `zxing-wasm@3.1.6`, set inside barcode-detector 3.2.3 | none |
| Backup digit reader (script tag) | `tesseract.js@5.1.1`, `dist/tesseract.min.js` | sha384 hash in `TESS_SRI` |
| Tesseract worker and core (fetched by Tesseract) | `tesseract.js@v5.1.1`, `tesseract.js-core@v5.1.1`, set inside Tesseract 5.1.1 | none |
| Tesseract English data | `@tesseract.js-data/eng@1.0.0`, `4.0.0_best_int` (`TESS_LANG`) | none |

## Why `ponyfill.js` and not `ponyfill.min.js`
The npm package ships no `ponyfill.min.js`. jsDelivr makes one on the fly, and those generated bytes can change when jsDelivr changes its minifier, which would break a hash without warning. The hashed file is the real file from the package, which jsDelivr serves unchanged.

## Known limits
- The hashes were computed from the published npm packages, and on 2026-11-01 the owner confirmed from a Windows PC that the files jsDelivr serves for these two URLs produce the same SHA-384 hashes (certutil). Re-check after any version change.
- If the script-tag load fails its hash, the app falls back to the ES module build at the same pinned version. That fallback has no integrity check, so today the hashes protect against accidental change, not against someone who controls the CDN files. To enforce them fully, first confirm the hashes against jsDelivr, then remove the ES fallback in `loadPolyfill`, accepting that a failed check then disables scanning.
- Nothing here is self-hosted. The scripts and data still come from a third party.

## Check the hashes against jsDelivr (one-time, needs internet)
```
curl -s https://cdn.jsdelivr.net/npm/barcode-detector@3.2.3/dist/iife/ponyfill.js | openssl dgst -sha384 -binary | base64
curl -s https://cdn.jsdelivr.net/npm/tesseract.js@5.1.1/dist/tesseract.min.js | openssl dgst -sha384 -binary | base64
```
Each should print the part after `sha384-` in `POLY_SRI` and `TESS_SRI` in `index.html`.

## Update to a newer version
In an empty folder:
```
npm pack barcode-detector@X.Y.Z tesseract.js@A.B.C
mkdir bd tess && tar xzf barcode-detector-X.Y.Z.tgz -C bd && tar xzf tesseract.js-A.B.C.tgz -C tess
openssl dgst -sha384 -binary bd/package/dist/iife/ponyfill.js | base64
openssl dgst -sha384 -binary tess/package/dist/tesseract.min.js | base64
```
Put the new versions in the URLs and the new `sha384-...` values in `index.html`. Run `CDN_PKG_DIR=<that folder> node tests/cdn-pins.test.cjs`. Then test scanning on a phone. If you change Tesseract's version, also check its default worker and core paths still use the same version, and that the English data path still exists.
